# 场景 1：系统可持续吞吐容量测试方案

## 1. 目标与结果定义

固定模型、部署、缓存和调度配置，测量同一批请求形状在不同到达强度下的完成吞吐与积压，给出 AISim 预测的可承受负载区间。

本次测的是包含 GPU、HBM、DRAM、SSD、PD 交接和调度约束的系统处理容量。系统容量占比不等于 GPU 算力利用率；需结合执行和等待记录判断限制来自哪里。

分别报告：

- 吞吐容量区间：没有持续积压的最高测试强度，与明确出现持续积压的最低测试强度。
- SLA 结果：沿用 TTFT ≤ 1 秒、TPOT ≤ 30 ms，列达标率。没有另行约定最低达标比例前，不把 SLA 合格上限与吞吐容量边界混为一谈。
- 8× 需求占比：8× 主要负载平均需求 / 容量边界对应的平均需求，仅用于同一 trace 形态、相同配置；同时列高峰与积压，不解释为硬件利用率。

该 trace 是非平稳有限负载。因此先得到“该负载形态下的容量区间”，不能仅凭一条轨迹或单个峰值宣称通用的理论最大 TPS。

## 4. 实验矩阵与顺序

首轮共 12 组：

| P DRAM | SSD 读带宽（GB/s/TP） | 压缩系数 |
|---:|---:|---|
| 256 GB | 2 | 1、2、4、8 |
| 128 GB | 2 | 1、2、4、8 |
| 64 GB | 2 | 1、2、4、8 |

按压缩系数由低到高，每档依次运行 256、128、64 GB。这样可以先覆盖所有配置的较低负载，再逐步推进。

已有三组系数 1 结果没有执行轨迹；为获得完整执行统计，首轮仍各重跑一次，旧结果用作一致性检查。先以一组小样本验证记录文件和计算量守恒，再启动全量矩阵。

若某配置系数 8 仍未出现明确容量边界，仅对该配置继续测 16、32……，不能直接将系数 8 当作最大容量。找到上下界后在两者之间补中点，最多先补两轮；若判断不明确，保留不确定区间，不强行给单值。实际耗时和空间先以首组完整记录结果测量，不沿用旧实验时长作承诺。

## 5. 必须记录与统计的内容

现有通用入口支持 --capture-scheduler-trace 和 --scheduler-trace-compression gzip；原扫参入口将 capture_scheduler_trace 固定关闭，本轮不能直接沿用其关闭记录的设置。

| 内容 | 口径 |
|---|---|
| 到达需求 | 请求/s、完整输入 token/s、预期输出 token/s |
| 完成吞吐 | 按请求结束时间统计请求/s；另列完成归属输出 token/s |
| P 实际计算吞吐 | 按 Prefill 执行批次记录 token 数；包含重算，排除已复用 KV |
| D 实际输出吞吐 | 核对执行记录的生成计数与报告定义；区分生成/采样 token 与已计算 KV 的 token，验证总量后按窗口统计 |
| P/D 执行忙碌比例 | 执行区间并集 / 窗口时长；跨窗口区间裁剪；不能用准入至结束时间代替 |
| BS、单轮 token | 记录分布、P95、最大值及达到调度上限的比例 |
| 未完成请求 | 已到达减已结束，记录精确峰值、窗口末数量和变化曲线 |
| P 等待与 KV 恢复 | 记录首次准入前调度和恢复等待、SSD 读任务及可用统计；不能直接把全部 P 待准入数归为算力排队 |
| 缓存与存储 | G1/G2/G3 复用、SSD 读写量、重算/抢占的可用计数 |
| 服务指标 | 平均/P99 TTFT、TPOT、联合 SLA 达标率 |

不要求本轮改引擎。先核对已支持的执行轨迹字段能否覆盖上述内容；不能覆盖的字段标为缺失，不以相近字段推算替代。

P 的批次 token 可按开始时间归属分桶；跨窗口的一轮须明确“整轮归属”口径，不能暗示知道轮内逐 token 完成时刻。忙碌比例使用裁剪后的真实执行区间。P/D 各一个 worker、DP1，执行比例可直接分角色计算。

使用三个统一窗口：

1. 主要负载：从首次到达到原 overlay.segment_ms / speedup。
2. 全到达：原完整到达跨度 / speedup；排空时间另列。
3. 高峰：每档强度按压缩后的到达需求选择相同的 5 分钟高输入量窗口，三档 DRAM 共用。不同强度重新按固定 5 分钟计算高峰，不能将原 5 分钟桶直接除以系数后仍称 5 分钟。

主要负载时段保留平均值与 5 分钟序列，并聚合成 1 小时观察积压是否持续增长。稀疏尾部能帮助系统排空，不能用全程最终“都完成了”判断主要时段可持续。

## 6. 容量边界判定

先看同配置随强度增加时的三组曲线：

- 到达需求与完成吞吐；
- 未完成请求数及其增长、消退；
- P/D 忙碌比例、实际计算/输出 token/s、KV 等待。

容量尚有余量的证据：提高到达强度后，完成吞吐随之提升；忙段积压能反复回落，主要负载期间没有持续上升趋势。

超过容量的证据：在持续有需求的多个连续小时里，完成吞吐无法跟随需求提高，未完成请求持续增长，且不是单个短暂突发。结合相同时间的输入量、请求形状、复用和实际执行量确认，避免把负载形状变化当作平台。

不以“窗口末积压很小”或“最高 BS 达到上限”单独判断容量。窗口末可能恰逢稀疏到达，BS 上限也可能是调度限制。若均值、时间曲线和增长趋势相互矛盾，结果标为待进一步验证。

每档先给低于边界的最高已测强度 L，以及高于边界的最低已测强度 U。用主要时段平均到达需求表述容量区间：

`C 位于 [0.241268 × L, 0.241268 × U) 请求/s`

这是该 trace 时间压缩负载族的经验容量区间，前提是两档已满足上述证据。没有发现明确上界时只报告已验证的下界；不能把最大观察完成吞吐直接当作可持续上限。若复用率大幅变化或吞吐非单调，应增加边界附近测试并保留解释。

8× 主要时段平均需求为 0.241268 请求/s。若容量区间为 [C_low, C_high)，其容量占比也应给区间，约为 (0.241268 / C_high, 0.241268 / C_low]，不报虚假的精确百分数。

## 7. 区分系统容量与算力限制

| 现象 | 支持的判断 |
|---|---|
| 有积压，KV 已就绪，P 持续执行 | P 执行路径可能受限，继续看算子耗时、HBM 和调度预算 |
| 有积压，P 经常空闲且请求等待恢复 | 存储/传输恢复可能受限 |
| P 顺畅，D 持续执行且 D 待处理增长 | D 路径可能受限 |
| BS/每轮 token 长期触顶 | 调度配置可能限制吞吐；不等于 GPU 达到峰值算力 |
| 缩容后实际计算量增加 | 同时存在缓存复用变化与重算，不能将全部损失归因于 SSD |

若首轮发现恢复限制，再针对该配置、同一接近边界的负载，只把 SSD 读带宽从 2 提高到 8 GB/s/TP，做单因素对照。该补测不属于首轮 12 组，也不提高其他带宽。

若领导进一步要求“去掉存储限制的计算执行上限”，需另设缓存/传输控制实验；本轮容量测试不能冒充这项结论。

## 9. 运行脚本与续跑

入口：scripts/run_throughput_capacity_sweep.py。

独立配置：configs/throughput_capacity/，共12份 YAML。每次运行还会在结果目录保存实际配置，命令行覆盖的内存预算也会反映在快照中。

默认采用完整8×包，按 speedup=1、2、4、8 依次运行；每档按 DRAM 256、128、64 GB 串行。进程树内存默认20GB。每组失败继续后续组，存在失败时整个脚本最后返回非零状态。

```bash
cd ~/project/aisimulate

OUT="$HOME/project/results/swe-chat-glm52-throughput-capacity"
mkdir -p "$OUT"
LOG="$OUT/sweep-$(date +%Y%m%d-%H%M%S).log"

nohup ~/.venvs/aisim/bin/python -u \
  experiments/disk_swe/scripts/run_throughput_capacity_sweep.py \
  --output-root "$OUT" > "$LOG" 2>&1 &

echo "PID=$!  LOG=$LOG"
tail -F "$LOG"
```

只检查矩阵：添加 --plan，不运行也不写结果。配置校验：添加 --dry-run，会写入配置快照并验证，但不启动仿真。

中断后续跑：沿用相同参数，添加 --resume /绝对路径/时间戳/sweep.json。默认完整12组可用：

```bash
~/.venvs/aisim/bin/python -u \
  experiments/disk_swe/scripts/run_throughput_capacity_sweep.py \
  --resume "$HOME/project/results/swe-chat-glm52-throughput-capacity/实际时间戳/sweep.json"
```

续跑会核对输入包、配置、内存参数、请求上限和引擎二进制身份，跳过状态完成且轨迹文件完整的组，重试失败或中断的组。非默认选择续跑时需重复原来的相关参数。不要同时启动两个进程续跑同一计划。

若系数8未达到上界，可新建一轮 --speedups 16 32，或用 --speedups 3 6 等参数细化。输出中仍会保存每组完整 YAML。

每组结果包括 requests.jsonl、prediction.json、iteration_metrics.jsonl.gz、scheduler_states.jsonl.gz、scheduling_events.jsonl.gz、scheduler_trace_metadata.json，以及运行日志和资源统计。计划在顶层 sweep.json，每组完成后附基础汇总。五分钟吞吐、忙碌比例和容量判断需用这些记录分析。

## 10. 小样本验证

- 每组4条请求，逐轮 Prefill 实际计算 token 均为2,357，与报告 committed_prefill_tokens 一致。

- speedup=2的到达时间为speedup=1的一半。
- 续跑两组均跳过，没有重复执行。
