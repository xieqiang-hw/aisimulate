# SWE-chat 场景 1 · MiniMax-M2.5 / H100 64 GB / 32×

沿用原 MiniMax 30 组扫描范围，采用 32× 会话叠加负载，模型替换为 MiniMax-M2.5，GPU 替换为 H100 SXM，并将 P、D 每张卡的**总 HBM 容量限制为 64 GB**。H100 的计算、HBM 带宽与互联参数保持不变，因此这是容量约束对照，不是 910B 性能仿真。原实验配置和结果文档保持不变。

## 1. 实验配置

| 项目 | 配置 |
|---|---|
| 模型 | MiniMaxAI/MiniMax-M2.5；FP8 block 权重／计算，Attention 与 KV 均为 BF16 |
| KV 精度 | BF16，显式 kvcache_quant_mode=bfloat16 |
| GPU | H100 SXM；单卡总 HBM 为 64,000,000,000 字节，即 64 GB ≈ 59.60 GiB |
| HBM 预算 | P/D 使用率均为 90%，自动计算可用 KV 容量 |
| 部署 | 1P1D，各 8 卡；Attention TP8/DP1，MoE TP1/EP8，共 16 卡 |
| P 本地缓存 | HBM + G2 DRAM + worker_local G3 SSD |
| P DRAM | 1000／512／384／256／128／64 GB，按 MiniMax KV 布局重新换算 |
| P SSD | 8 × 7 TB ≈ 56 TB；读 1／2／4／8／16 GB/s/TP，写固定 8 GB/s/TP |
| D 本地缓存 | 仅 HBM，关闭 G2 和本地 G3 |
| H2D / D2H | 各 25 GB/s/TP 分片，TP8 均匀并行时折合节点各 200 GB/s |
| PD 交接 | 保留直通，50 GB/s/TP，destination_missing，不经过盘框 |
| 上下文上限 | 131,072 token（128K），沿用原输入与输出合计筛选条件 |
| 单步 token 预算 | P/D 均为 16,384 |
| 活跃序列上限 | P 32，D 256 |
| 回放 | 仅标称 32× 会话叠加，speedup=1，607,190 条请求 |
| SLA | TTFT ≤ 1 秒，且单请求平均 TPOT ≤ 30 ms |
| 执行 | 30 组串行，先按读带宽升序、同一带宽内按 DRAM 升序；主机预算默认自动 |
| 调度观测 | 默认开启 capture-scheduler-trace，scheduler-trace-compression=gzip |
| 性能估算 | op_level，SILICON，vLLM 0.24.0，禁止估算器回退 |

读带宽均按每 TP 分片计，节点等效为 8／16／32／64／128 GB/s；节点等效写带宽为 64 GB/s。读写方向沿用引擎的分别限速方式。

## 2. 单卡 HBM 容量核算

以下为 AISim 原生内存估算及回放容量解析实际返回值，P/D 在此配置下相同；GB 均为十进制。

| 用途 | 单卡容量（GB） |
|---|---:|
| 总 HBM | 64.000000 |
| 90% 使用预算 | 57.600000 |
| 模型权重（TP8/EP8 后） | 28.677538 |
| 激活与临时空间估计 | 2.013266 |
| 运行时预留 | 3.758096 |
| 通信预留 | 0.411042 |
| 剩余 KV 字节预算 | 22.740058 |
| 按整块取整后的 KV | 22.739878 |
| 未划入 90% 预算的余量 | 6.400000 |

自动 KV 容量：**P、D 每卡均为 11,193 块，覆盖 716,352 token 位置**。TP8 保存同一批 token 的不同 KV 分片，因此 token 容量不能再乘 8。

一条完整 128K 请求需要 2,048 块、单卡约 4.161 GB KV。仅按容量可放约 5 条完全独立、接近 128K 的全长 KV；实际并发还取决于前缀共享、请求长度、计算和调度，不能把这个数直接视为系统最大并发。

本轮显式配置为 gemm_quant_mode=fp8_block、moe_quant_mode=fp8_block、fmha_quant_mode=bfloat16、kvcache_quant_mode=bfloat16。权重容量近似 W8A8，但计算耗时仍来自 H100 FP8，不是昇腾 INT8。

这里限制的是总 HBM，而不是把 KV 设为 64 GB。MiniMax 的权重和每 token KV 比 GLM 小，所以总 HBM 缩到 64 GB，也不意味着可缓存的 token 数比原 GLM/H200 更少。

## 3. G2 / G3 块数换算

MiniMax 为 62 层、8 个 KV heads、head_dim=128；TP8 每卡持有 1 个 KV head，BF16 KV 元素为 2 字节：

~~~text
每 token、每卡 = K/V 两份 × 62 层 × 1 KV head × 128 × 2 字节
              = 31,744 字节
每块、每卡    = 31,744 × 64 = 2,031,616 字节
每块、TP8节点 = 2,031,616 × 8 = 16,252,928 字节
缓存块数      = round(目标字节数 ÷ 16,252,928)
~~~

一块覆盖 64 个连续 token 的全部 62 层 KV；各卡存自己的 TP 分片。输入 trace 中 hash_ids 的 16 token 粒度与引擎 64 token KV 块不是同一单位。

| P DRAM 标称容量 | num_host_blocks | 实际容量（GB） |
|---:|---:|---:|
| 1000 GB | 61,527 | 999.993901 |
| 512 GB | 31,502 | 511.999738 |
| 384 GB | 23,627 | 384.007930 |
| 256 GB | 15,751 | 255.999869 |
| 128 GB | 7,876 | 128.008061 |
| 64 GB | 3,938 | 64.004030 |

SSD：num_g3_blocks = **3,445,533**，实际约 **55.999999771 TB**。不沿用 GLM 的 G2/G3 块数。

## 6. 运行与验证

配置：configs/swe_minimax_h100_64gb_ep8_p*gb_read*_overlay_32x.yaml。\
入口：scripts/run_minimax_h100_64gb_32x_sweep.py。\
硬件覆盖：configs/systems_h100_64gb/h100_sxm.yaml。

hardware 仍为 h100_sxm，以复用对应算子数据库；独立 systems_paths 优先加载 64 GB 配置，不修改官方硬件文件。

查看计划：

~~~bash
cd ~/project/aisimulate
~/.venvs/aisim/bin/python experiments/disk_swe/scripts/run_minimax_h100_64gb_32x_sweep.py --plan
~~~

启动 30 组，并自动更新 MD 和 HTML：

~~~bash
cd ~/project/aisimulate
OUT="/mnt/d/aisim-results/swe-chat-minimax-h100-64gb-ep8-32x-bf16kv"
mkdir -p "$OUT"
LOG="$OUT/sweep-$(date +%Y%m%d-%H%M%S).log"
nohup ~/.venvs/aisim/bin/python -u \
  /home/xieqiang/project/tmp/launch_minimax_h100_64gb_32x.py \
  --output-root "$OUT" > "$LOG" 2>&1 &
echo "PID=$! LOG=$LOG"
tail -F "$LOG"
~~~

入口固定开启 --capture-scheduler-trace --scheduler-trace-compression gzip。保持 30 组串行，读带宽优先升序，同带宽内 DRAM 升序；主机内存预算默认自动，可额外添加 --memory-limit-gb 20。

默认记录 P/D 每轮执行与调度状态，生成 iteration_metrics.jsonl.gz、scheduler_states.jsonl.gz、scheduling_events.jsonl.gz 和 scheduler_trace_metadata.json，用于后续 BS、忙碌比例、计算 token 与等待原因分析。即使命令省略两个观测参数，本入口也默认开启 gzip 调度轨迹。

默认自动选择主机内存预算；如需固定每组预算，可添加 --memory-limit-gb 20。串行运行，单组失败后继续后续组，状态保存在 sweep.json。实验结果保存于 D 盘；后台程序在有新结果时同步更新本表和同名 HTML。
