情况一：序列没满，token 预算已满

调度器先安排运行中的请求。一个长请求可独自消耗整轮 16,384 token，因而 BS 只有 1，也没有剩余 token 预算加入新请求。Chunked Prefill 允许切块，不保证把每轮预算平均分给多个请求。

情况二：批次提前提交，不能再插入

原请求输入 17,486 token，复用 128 token，剩余正好是 16,384 + 974。三条新请求在第一批计算期间到达；当前异步调度模型将后续尾段视为已提交，它们在尾段结束后才进入下一批。

这些图能够说明什么？

低五分钟平均忙碌占比，不排除十几秒内连续计算并形成等待。 原窗口 P 约计算了 49.37 秒，普通准入队列非空约 12.36 秒；按调度状态快照还原，这些普通队列等待时段与 P 计算重叠。

BS 上限和 token 预算是两个独立限制。 BS 未到 32，不意味着这一轮一定还能加入请求。异步批次已提交时，即使两项都未满，新到请求也可能只能等待后续批次。

这两例不等于 GPU 算力已经吃满。 它们说明当前调度约束确实影响准入时机；提高预算或改变异步调度是否改善延迟，仍需单因素对照。情况二是 AISim 当前的建模行为，尚未用实机核对其与对应 vLLM 版本是否完全一致，也不能用于解释全部长尾 TTFT。

数据来源与统计口径

计算批次来自 iteration_metrics.jsonl.gz；普通队列状态来自 scheduler_states.jsonl.gz，采样边界为调度后、发出执行前；等待曲线来自 requests.jsonl，Q(t)=到达时刻≤t且首次准入时刻>t的请求数，时间相同的事件合并处理。输入长度包含可复用前缀，上图仅统计实际新计算 token。

原五分钟窗口为第 7.9027778–7.9062500 天。为完整展示情况一的第五批，图表范围额外延长约 0.434 秒；不把该延长段当作原五分钟汇总。异步提交规则见 vllm/core.rs 的 first_pass_admitting_arrival 与等待队列 admissible_from_pass 检查；默认批次深度由 engine/config.rs 的 max_concurrent_batches 决定。
