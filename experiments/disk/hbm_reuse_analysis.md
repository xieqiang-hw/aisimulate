# DRAM 复用偏低与 HBM 高复用的实验分析

各层复用占比按首次准入时复用的 token 数除以全部输入 token 数计算，长请求权重更大。SSD 恢复经 DRAM 中转的部分计入 G3。联合 SLA 为 TTFT ≤ 5 秒、ITL ≤ 50 ms。SSD 带宽均按每 TP 分片计，容量和流量使用十进制 GB、TB。

## 3. 更换模型和 GPU

为了向单卡 64 GB 的 910B3 容量靠近，先尝试 A100 80 GB，再选原生支持 FP8 的 H100 SXM 80 GB 作为对照。最初 GLM／A100 方案为 P 侧 DP2×TP16／EP32、D 侧 DP16×TP2／EP32。P 本地 G3 当前要求 Attention DP1，并要求对应 G2 为 dp_rank_local。G2 本身可以支持 DP>1，但当前缺少 P、D 各自共享一个独立池的选项。双侧 cluster_shared 会共用一个池，并要求两侧布局匹配。这些约束阻碍了原定异构并行方案。

支持 P 侧 Attention DP>1 与本地 G3 并用，属于中等规模的引擎改造。当前回放在配置校验和角色工厂初始化两处都限制 G3 为 DP1。放宽校验后，需要明确同一 P worker 内多个 DP rank 如何共用本地 SSD，同时让恢复的 KV 进入发起请求的 rank 自己的 G2。SSD 的容量和读写带宽要由这些 rank 共同消耗，避免随 DP 数重复计入。还要验证并发写入、同一前缀的并发恢复、淘汰与未完成 I/O 的协调，以及分层复用统计。可以先以 P 侧 DP2、各 rank 独立 G2、同一 P worker 共用 G3 为最小验证范围，再验证原定 P、D 不同 TP 布局下的 KV 交接。若还要求 P、D 分别拥有各自的跨 rank G2 共享池，则还需单独实现按角色划分的 G2 池。

## 4. 是否增加暖机

暖机是在评分前执行历史请求以建立缓存。16 周原实验连续回放全部历史，初始冷启动发生在开头，而全场 HBM 复用已经较高。针对低 DRAM 复用这一问题，增加前置暖机预计难以改变主要现象，因此暂未做专门的暖机对照。

这一项属于分析判断，尚无暖机 A/B 结果。初始冷启动影响的请求数也未单独量化。


## 5. 缩减 P 侧 HBM KV 池（128K、1×）

使用第 1 节的 16 周 FreeInference 128K 原速数据（665,415 条），沿用 H200／GLM-5.2-FP8、1P1D、Attention TP8、MoE TP8／EP1。固定 P 侧 DRAM 384 GB、SSD 约 56 TB（读写各 8 GB/s/TP 分片）及 D 侧原配置。只将 P 侧 `kv_cache.capacity` 改为 `type: fixed`，扫描 `blocks`。每块对应 64 个 token 位置，容量按整个 P 侧 TP8 实例约 30.83 MB/块换算。

单条 131,072 token 按 64 token/块换算是 2,048 块。

## 6. 时间叠加与 SSD 带宽扫描

旧 speedup 方法与 Saki 一致，将全部请求的相对到达时间除以倍率。新方法把 16 周切成等长段，再整体前移并叠到第一段，保留各段内部的请求间隔和前缀身份。2×／4×／8× 对应 8／4／2 周时间轴。5×、6× 切点落在周中，跨切点的会话可能被拆到新时间轴两端。所有叠加 trace 以 engine speedup=1 回放。

这些实验沿用 GLM-5.2-FP8／H200、1P1D、Attention TP8、MoE TP8／EP1，以增加不同会话的前缀竞争，并观察 DRAM 缩容后的 SSD 带宽依赖。
